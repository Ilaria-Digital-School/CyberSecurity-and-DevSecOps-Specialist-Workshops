# Map the Blog's attack surface

THEORETICAL RECAP The attack surface is the sum of all points where an unauthorized actor can attempt to enter, extract, or manipulate data within a system. It includes entry points (HTTP endpoints, forms, APIs, file uploads, cookies, headers), data flows crossing trust boundaries, and the assets those flows expose. A useful mental model: imagine the application as a building. Doors, windows, air vents, and delivery hatches are your entry points; the trust boundaries are the walls separating public zones from restricted rooms; and the valuables inside are your assets. Reducing the attack surface means having fewer doors, stronger walls, and knowing exactly what each door leads to. A practical way to enumerate the surface is to walk every input a user (authenticated or not) can control, then map it to the component that processes it and the data it touches. Common mistakes include focusing only on the visible UI while ignoring APIs, admin panels, and third-party integrations; forgetting unauthenticated endpoints; confusing 'attack surface' (entry points) with 'attack vectors' (methods) or 'threats' (STRIDE categories); and omitting infrastructure surfaces such as exposed ports, the database, and the CI/CD pipeline. Mini example: a blog comment form is an entry point. It crosses the trust boundary from anonymous internet to the application server, reaches the comment-processing logic, and writes to the database.
