# Document network status

THEORETICAL RECAP Documenting network status means capturing a reliable snapshot of what your Linux host exposes and communicates on the network at a given moment. The core mental model is a layered inventory: interfaces (link and IP configuration), listening sockets (services waiting for connections), active connections (established sessions), and the processes that own them. Each open port is an attack surface; each unexpected connection is a potential indicator of compromise. Key tools you already practiced: 'ip' inspects interfaces, addresses and routes (replacing legacy 'ifconfig' and 'route'); 'ss' lists sockets far faster than 'netstat', with flags such as -t (TCP), -u (UDP), -l (listening), -n (numeric), -p (owning process); 'netstat' remains a fallback on older systems. Pair these with process tools ('ps', signals, systemd) so every open port maps to a named service. Common mistakes: running 'ss' or 'netstat' without sufficient privileges, which hides the owning PID/program; forgetting to distinguish 'listening' from 'established' sockets; ignoring both IPv4 and IPv6; and confusing 0.0.0.0 (all interfaces, publicly reachable) with 127.0.0.1 (loopback only, local). Mini example: 'sudo ss -tulpn' outputs a listening TCP socket on 0.0.0.0:22 owned by process 'sshd'. Reading this correctly, you conclude that SSH is exposed on every interface — a fact worth documenting and justifying from a security standpoint. WORKSHOP BRIEF Your objective is to produce a professional-grade network status document for a Linux host (your own machine, a VM, or a container).
