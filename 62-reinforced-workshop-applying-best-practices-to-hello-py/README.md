# Reinforced workshop: applying best practices to hello.py

THEORETICAL RECAP Secure scripting best practices are not optional additions — they are the foundation of any professional automation script, especially in a security context. When you write a Python script intended for security tasks, several non-negotiable rules apply. First, the shebang line (#!/usr/bin/env python3) ensures your script runs with the correct interpreter regardless of the system environment. Second, file permissions must be set correctly: a script that handles sensitive data should never be world-readable or world-writable (use chmod 700 or 750 as a baseline). Third, secrets — API keys, passwords, tokens — must never be hardcoded in the source code. They belong in environment variables or dedicated secret management systems. Fourth, your script should handle errors gracefully using try/except blocks and provide meaningful output rather than raw tracebacks. A common mistake beginners make is writing functional code first and treating security hygiene as an afterthought. In professional environments, this mindset creates vulnerabilities that are exploited at the scripting layer itself. Mental model: think of your script as a small application exposed to a hostile environment — every input is untrusted, every secret is a liability if exposed, and every permission is a potential attack surface. Example: a scanner script that prints 'Hello, [username]' fetched from an environment variable is already safer than one that hardcodes the username or reads it from an unprotected config file.
