# Develop a test checklist based on the threat model

THEORETICAL RECAP A threat model is a structured description of what can go wrong in an application: assets to protect, entry points (attack surface), threats (typically classified via STRIDE: Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege), and the risk score attached to each threat (OWASP Risk Rating = Likelihood × Impact). A test checklist is the operational translation of that model: for each prioritized threat, you define one or more concrete, verifiable tests that prove whether the corresponding control exists and works. The correct mental model is a traceability chain: Asset -> Entry point -> Threat (STRIDE) -> Risk score -> Test(s) -> Expected result. Nothing in your checklist should exist without a threat behind it, and no high-risk threat should be left without a test. Common mistakes: writing vague tests ("check the login is secure"), testing technologies instead of threats, ignoring risk scores so that low-risk items get as much attention as critical ones, and forgetting non-functional threats like DoS or repudiation (missing logs). Mini example: Threat = 'Tampering with the price field on the checkout API', Risk = High. Tests: (1) send a modified price in the request body and confirm the server recalculates from the catalog; (2) verify server-side validation rejects negative values; (3) confirm the manipulation attempt is logged. WORKSHOP BRIEF Your objective is to transform an existing threat model into a prioritized, actionable security test checklist for a web/API application.
