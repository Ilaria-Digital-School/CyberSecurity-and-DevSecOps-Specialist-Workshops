# Scan /var/log/auth.log for detections

THEORETICAL RECAP On Debian-based Linux systems, /var/log/auth.log records authentication and authorization events: SSH connections (successful and failed), sudo invocations, su attempts, PAM messages, and session open/close events. On RHEL-based systems the equivalent is /var/log/secure, and journald may also hold these entries (journalctl -u ssh). The mental model to adopt: auth.log is a chronological, append-only text stream where each line follows the pattern 'timestamp hostname process[pid]: message'. Detection work means turning this raw stream into signals — repeated 'Failed password' lines from the same IP indicate brute-force; 'Accepted password' or 'Accepted publickey' shows successful logins; 'sudo: ... COMMAND=' reveals privilege use; 'Invalid user' points at username enumeration. A clear example: the line 'Failed password for invalid user admin from 203.0.113.5 port 44921 ssh2' tells you an attacker tried a non-existent account from a specific IP. Count these per IP and you find your attackers. Common mistakes: forgetting the file requires root or the adm group to read; parsing timestamps naively (syslog format has no year); confusing 'invalid user' with a valid failed login; using overly greedy grep patterns that produce false positives; and analyzing a rotated/truncated file (check auth.log.1, auth.log.2.gz with zgrep). Keep detections reproducible: prefer scripted, documented commands over ad-hoc one-liners you cannot repeat.
