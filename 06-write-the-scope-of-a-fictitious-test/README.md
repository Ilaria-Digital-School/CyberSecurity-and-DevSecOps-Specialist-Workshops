# Write the scope of a fictitious test

Theoretical Recap on Scoping Defining the scope of a security test is the foundational step that separates an authorised, professional engagement from unauthorised activity. The scope is a formal document that explicitly details what is permitted for testing. It functions as a legal and operational contract between you, as the tester, and the client. A clear scope includes the target systems, networks, or applications, the testing methods allowed, and crucially, what is off-limits. A useful mental model is to think of it as drawing a bright red line around the exact area you are authorised to operate within. Everything inside that line is your playground; anything outside is strictly forbidden. Common mistakes include defining targets too vaguely, such as "the corporate network," which is dangerously broad. Another frequent error is omitting explicit rules of engagement, like permitted data access levels or acceptable testing times. This vagueness can lead to accidental breaches of policy or law. Consider a small example: a client authorises you to test their customer-facing web application at 'shop.example.com'. A well-defined scope would state that the test is limited to this specific subdomain, using only the HTTPS port. It would forbid any testing against their internal employee portal or their cloud hosting provider's infrastructure. This precise definition protects both parties.
