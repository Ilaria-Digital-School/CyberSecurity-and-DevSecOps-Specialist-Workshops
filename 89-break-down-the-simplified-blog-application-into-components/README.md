# Break down the simplified Blog application into components

THEORETICAL RECAP Threat modeling always starts with understanding what you are protecting. Before you can identify threats, you must decompose the application into its components. A component is any distinct part of the system that stores, processes, or transmits data: a web frontend, a backend API, a database, an authentication service, a file storage, or an external dependency. The standard mental model is to view the application as a set of nodes (components) connected by data flows (requests, responses, queries), grouped into trust boundaries (zones where the level of trust changes, for example between the browser and the server, or between the server and the database). A useful way to think about it: 'processes' do work, 'data stores' hold information, 'external entities' interact from outside (users, third-party APIs), and 'data flows' move data between them. This vocabulary comes directly from Data Flow Diagrams (DFD), the backbone of threat modeling. Common mistakes: confusing a feature (e.g. 'comment') with a component (e.g. 'comment service + comments table'); forgetting trust boundaries; ignoring external dependencies like a CDN or an email service; or listing technologies without describing the data they handle. Mini example: In a Todo List, components include the browser (external entity), the web server (process), and the tasks database (data store), with a trust boundary between browser and server.
