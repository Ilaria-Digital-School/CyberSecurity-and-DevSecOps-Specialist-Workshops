# Red thread 2 — Model and document the threats of a Weather API

## Context You are hired as a junior security analyst for a startup that publishes a public REST **Weather API**. This API exposes endpoints such as `GET /weather?city=`, `GET /forecast?lat=&lon=`, `POST /users` (registration), `POST /login` (authentication with JWT), `GET /api-keys` (management of consumer API keys) and a premium tier accessible via API key + rate limiting. The API relies on a backend service, a cache layer (Redis), a relational database (PostgreSQL) and calls one external third-party meteorological data provider. The company wants a **complete threat model** before starting any pentest, in order to prioritize security tests and corrections. Your job is to model this API end-to-end, apply STRIDE systematically, rate the risks, and turn the model into an actionable, versioned test checklist — exactly the chain you built through Red thread 1 and the preceding activities. ## What you will produce A reusable threat-modeling package for the Weather API: a Data Flow Diagram (DFD), a STRIDE threat catalog, a risk rating table, a derived security test checklist mapped to threats, and short documentation with versioning conventions. This mini-project directly reinforces the skill block "Understand the risks of an application to prioritize tests and corrections" and prepares the pentest blocks that follow. ## Scope - **In scope:** all public and authenticated endpoints, the JWT auth/session flow, API-key management, the cache and database interactions, and the outbound call to the third-party weather provider. - **Out of scope:** exploitation/live pentest (this comes later in the course).
