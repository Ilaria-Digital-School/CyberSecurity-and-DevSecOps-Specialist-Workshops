# Adapting the checklist to a third party public API

THEORETICAL RECAP A security test checklist derived from a threat model is not a fixed artifact: it must be adapted to the specific context of the target. A third-party public API differs sharply from an internal service. Key definitions: a 'third-party public API' is an interface exposed on the internet, owned or operated by an external provider, that you consume but do not fully control. Your attack surface is therefore split between what you can test (your usage, keys, integration) and what you cannot legally or technically touch (the provider's backend). The mental model to keep: 'trust boundary at the edge'. Every request crossing from your system to the third party, and every response coming back, is a place where STRIDE threats (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege) apply, and where OWASP Risk Rating helps you prioritize what to verify first. Common mistakes: copying an internal checklist without removing items you have no authority to test; ignoring rate limiting and quota abuse (DoS/cost impact); forgetting secret management for API keys and tokens; and assuming the provider validates input for you. Mini example: consuming a public weather API, a naive checklist keeps 'test SQL injection on backend'. That is out of scope. Instead it should read 'verify the API key is not exposed client-side' and 'confirm TLS certificate validation is enforced' — items you actually own.
