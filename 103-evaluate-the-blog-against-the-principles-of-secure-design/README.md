# Evaluate the Blog against the principles of secure design

THEORETICAL RECAP Secure design principles are foundational rules that guide how an application should be architected to minimize attack surface and contain damage when a component is compromised. The core principles you must know include: Least Privilege (every component, user, and process gets only the permissions strictly required), Defense in Depth (multiple independent layers of control so no single failure is catastrophic), Fail Securely (errors default to a denied/safe state, not an open one), Complete Mediation (every access to a resource is checked, never cached or bypassed), Economy of Mechanism (keep designs simple and auditable), Separation of Duties, Secure Defaults (the out-of-the-box configuration is the safe one), and Minimize Attack Surface (expose only what is necessary). A useful mental model: imagine your Blog as a castle. Least Privilege means each servant holds only the keys they need. Defense in Depth means a moat, walls, guards, and locked doors — an attacker breaching one must still defeat the rest. Fail Securely means a broken gate slams shut rather than swinging open. Common mistakes: treating authentication as the only control (no depth), granting the database user admin rights 'to save time' (privilege creep), verbose error messages leaking stack traces (insecure failure), and checking permissions only at the UI level while the API stays open (broken mediation). Mini example: a 'delete post' endpoint that verifies the JWT is valid but never checks the caller owns the post violates Complete Mediation and Least Privilege — any authenticated user can delete any post.
