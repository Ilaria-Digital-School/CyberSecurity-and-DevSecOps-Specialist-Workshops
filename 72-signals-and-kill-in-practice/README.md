# Signals and kill in practice

THEORETICAL RECAP A signal is an asynchronous software interrupt sent to a process by the kernel, another process, or the user. It tells the process something happened and, unless caught or ignored, triggers a default action. Each signal has a name and a number: SIGTERM (15) politely asks a process to terminate and can be caught to clean up; SIGKILL (9) forcibly kills it and cannot be caught, blocked, or ignored; SIGINT (2) is what Ctrl+C sends; SIGHUP (1) is often used to reload configuration; SIGSTOP/SIGCONT pause and resume; SIGSEGV signals an invalid memory access. Mental model: think of signals as knocks on a process's door. Most knocks can be answered by a handler (custom code the process runs on reception). SIGKILL and SIGSTOP are the only knocks the process cannot refuse because the kernel handles them directly. The kill command sends signals despite its name: `kill -TERM ` or `kill -9 `. `pkill` and `killall` target by name; `kill -0 ` tests existence without sending a real signal. Common mistakes: jumping straight to `kill -9`, which prevents graceful cleanup and can corrupt data or leave locks; confusing PID with job number; forgetting that you can only signal processes you own (unless root); assuming a zombie can be killed (it cannot, you must reap its parent).
