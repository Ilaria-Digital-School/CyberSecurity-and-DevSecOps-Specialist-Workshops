# Draw the DFD for the Blog application

THEORETICAL RECAP A Data Flow Diagram (DFD) is a graphical model that shows how data moves through an application. It relies on four core symbols: external entities (rectangles) representing actors or systems outside your control (users, third-party APIs, browsers); processes (circles or rounded rectangles) representing logic that transforms data (authentication, post creation, comment handling); data stores (open-ended rectangles or parallel lines) representing where data rests (database, cache, file storage); and data flows (arrows) representing the movement of data between elements, each labeled with what actually travels (credentials, session token, post content). The essential mental model: follow the data, not the code. Ask yourself "who sends what, to whom, and where is it stored?". The single most important concept for security is the trust boundary: a dotted line crossing data flows wherever the level of trust changes (browser to server, application to database, application to third-party API). These boundaries are exactly where threats concentrate, and they will feed your STRIDE analysis in the next steps. Common mistakes to avoid: drawing a flowchart instead of a data flow (a DFD shows data, not control sequence); forgetting to label flows; omitting trust boundaries; and mixing abstraction levels. A mini example: a Level 0 (context) DFD of a login shows [User] --credentials--> (Authentication Process) --query--> [User Database], with a trust boundary between the User and the Authentication Process.
